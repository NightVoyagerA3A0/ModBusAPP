# GlobalPlan

## 当前项目状态

### 项目定位
- 这是一个以 Modbus 通信、设备建模、数据映射和 WPF 展示为核心的学习型项目。
- 当前代码既包含实验性质较强的练习代码，也已经开始形成真正可复用的业务层结构。

### 当前已有结构
- `Device.cs`
  - 定义设备模型、寄存器/线圈特性、点位类型与拼接类型。
  - 当前项目的“声明层”核心基本在这里。
- `Interface.cs`
  - 定义 `IDeviceModel` 与缓存接口。
  - 负责提供业务层与设备模型之间的约定。
- `Components.cs`
  - 旧版组件层，包含串口适配、DataMapper、缓存结构和未完成的 MappingHelper。
  - 当前仍保留大量实验性、未完成和不可达代码。
- `ComponentsVibeCode.cs`
  - 新版核心业务层。
  - 已具备运行期绑定、读取计划、原始快照建模、寄存器/线圈映射与设备回填能力。
- `Program.cs`
  - 当前仍以控制台试验代码为主，包含委托、异步尝试、PollMission 的雏形。
  - 已做最小修复，项目现在可以编译。
- `GUI.xaml` / `GUI.xaml.cs`
  - 当前是 WPF 可视化壳，尚未和核心业务层建立真正的数据绑定闭环。
- `VisibleUserInterface.cs`
  - 当前仍为空，后续可以决定保留为界面协调层，或删除。

### 当前编译状态
- 项目目前已经可以成功编译。
- 仍存在若干 warning，主要集中在：
  - `Components.cs` 中的不可达代码与空引用风险
  - `Program.cs` 中的实验性异步与未使用变量
  - `NModbus4` 包与目标框架之间的兼容性 warning

## 总体开发目标

建议把项目分成四个逐步落地的目标：

1. 让“通信 -> 映射 -> 设备模型”这条主链路稳定可复用
2. 让“轮询任务管理”从实验代码中独立出来
3. 让 WPF 界面真正消费运行时数据
4. 在保留学习性的同时，逐步淘汰旧实验代码

## 分阶段计划

### 第一阶段：收口核心业务层
目标：让 `ComponentsVibeCode.cs` 成为明确主线。

建议任务：
- 用 `ComponentsVibeCode.cs` 作为后续主业务层，不再继续扩展旧 `DataMapper` 逻辑。
- 为 `ModbusDeviceRuntime<TDevice>` 增加一段最小示例流程，验证：
  - 创建设备模型
  - 构造读取快照
  - 执行映射
  - 回填到设备对象
- 明确 `Custom` 拼接在 `IDeviceModel.TryJoint(...)` 中的真实实现策略。
- 视情况增加针对寄存器拼接、快照应用、读取计划生成的测试或示例代码。

阶段完成标准：
- 新业务层能够被一个最小调用样例稳定使用。
- 使用者能清楚知道后续应该依赖 `ComponentsVibeCode.cs`，而不是旧 `Components.cs`。

### 第二阶段：整理 PollMission
目标：把轮询任务从 `Program.cs` 的实验区中拆出来。

建议任务：
- 将 `PollMission` 抽离为单独文件，建议命名为带 `VibeCode` 后缀的新文件。
- 在该类中明确三类职责：
  - 串口资源创建与释放
  - Modbus 主站对象生命周期
  - 轮询循环、停止控制、异常处理
- 为 `TryCreate(...)` 补足真正的初始化状态，而不只是返回可编译对象。
- 考虑后续是否需要引入：
  - `CancellationTokenSource`
  - 轮询状态
  - 端口占用表
  - 日志输出接口

阶段完成标准：
- `PollMission` 不再只是“可编译的壳”，而是能真实承接轮询任务。
- `Program.cs` 不再承担任务类定义职责。

### 第三阶段：决定旧组件层去留
目标：减少双轨结构带来的困惑。

建议任务：
- 对 `Components.cs` 做一次明确决策：
  - 保留并逐步清理
  - 标注为旧实验文件
  - 或拆分后淘汰
- 如果继续保留：
  - 清理 `MappingHelper` 中的不可达代码
  - 清理 `DataMapper` 中控制台试探式输出
  - 统一命名与空引用处理
- 如果决定淘汰：
  - 在文件头明确标注“旧实验版本，不再作为主线使用”

阶段完成标准：
- 项目中只保留一条清晰的“核心业务层主线”。
- 新加入的人不会在 `Components.cs` 和 `ComponentsVibeCode.cs` 之间摇摆。

### 第四阶段：接入 WPF 界面
目标：让界面从占位壳升级为真正的监控面板。

建议任务：
- 明确 UI 要展示的第一批信息：
  - 端口状态
  - 设备在线状态
  - 当前温度点位值
  - 线圈状态
  - 最近告警
- 建立一个适合 WPF 的 ViewModel 层。
- 将 `ModbusDeviceRuntime<TDevice>` 的结果转换为界面可绑定的数据对象。
- 用状态栏展示通信状态，用主面板展示实时点位。

阶段完成标准：
- 启动界面后，能够看到来自设备模型的实时或模拟数据。
- UI 与通信/映射层之间有清晰边界。

### 第五阶段：学习型项目完善
目标：让项目不仅能跑，也便于复盘和继续学习。

建议任务：
- 对所有新加入的 VibeCode 文件继续遵守：
  - 中文 XML 文档
  - 高注释率
  - 单独 Questions 文件
- 为关键模块逐步补充问题文件，例如：
  - `ProgramQuestions.md`
  - `PollMissionVibeCodeQuestions.md`
  - `DeviceQuestions.md`
- 形成“每完成一个模块，就附带知识问题”的节奏。

阶段完成标准：
- 这个项目既像工程，也像个人知识仓库。
- 后续回看时，能够快速知道每个模块在学什么、解决什么问题。

## 当前优先级建议

建议按下面顺序推进：

1. 先确认 `ComponentsVibeCode.cs` 的最小使用样例
2. 再把 `PollMission` 抽离为独立 VibeCode 文件
3. 然后处理 `Components.cs` 的旧逻辑去留
4. 最后再真正推进 WPF 绑定和界面交互

原因：
- 先收口核心业务层，后面才不会反复返工。
- 如果轮询层还不稳定，太早做 WPF 会让界面跟着不停改。
- 旧组件层不先定性，项目结构会一直显得混乱。

## 当前风险与注意点

- `NModbus4` 当前存在兼容性 warning，后续要关注长期可维护性。
- `Components.cs` 和 `ComponentsVibeCode.cs` 并存，会让主线不够清楚。
- `Program.cs` 仍然承载了过多实验性内容，不适合作为最终入口形态。
- `GUI.xaml` 还没有真正绑定业务层，现在更像界面草图。
- `Custom` 拼接目前只有接口约定，尚未体现真实设备场景。

- 最后提交一次“WPF 接入”

推荐把提交拆小，这样更利于学习和回滚。
